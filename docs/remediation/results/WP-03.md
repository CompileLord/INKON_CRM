## Behavior and migration

Refresh issuance uses a random 32-byte URL-safe `jti`, canonical user-ID `sub`, and `type=refresh`. One AuthService issuance helper is used by login, rotation, set-password, and password-reset confirmation. Refresh validates signed purpose, subject, token ID and time claims before conditionally consuming the stored hash for that subject, with revocation and database expiry predicates. `UPDATE RETURNING` produces one winner; successor insertion shares the caller's existing transaction. The dependency commits successful requests and rolls back exceptions. Logout consumes only the supplied identity-bound credential and remains idempotent for invalid credentials.

Model and migration use a unique partial index on unrevoked token hashes. Existing rows and hashes are preserved; upgrade revokes every previously active credential before adding that index, so ambiguous legacy sessions must sign in again. Neither user ownership nor colliding hashes are rewritten. Downgrade restores the old lookup index but does not restore any revoked credential. A rollback to old application code is not a safe remediation strategy; keep refresh disabled or roll forward. No deployment or operational migration was performed.

Migration revision `c9e3f0a1b2c4` follows the prior single head `d8e9f0a1b2c3` in the new authorized file `rwp03_refresh_identity.py`. The disposable rehearsal creates the prior schema, seeds two active legacy rows sharing a hash, upgrades, probes live-hash uniqueness, and downgrades. Original row IDs `[1, 2]` remain present and revoked throughout recovery. The separate row inserted after upgrade is an index probe, not an original legacy credential.
