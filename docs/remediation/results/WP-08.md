## Behavior and review

FinanceService centralizes reversal eligibility after acquiring the accepted student-account lock. Both void and refund reject an existing void; void also rejects any prior refund. The original error messages, cash/wallet refund behavior, cumulative refund limit, Decimal arithmetic, authorization and caller-owned transaction remain intact. Eligibility reads precede any mutation and use bounded existence lookups. No migration, response schema or unrelated financial behavior changed.

Sequential tests cover cash/wallet and partial/full permitted refunds, void-then-refund and refund-then-void. They seed a payment of 100, an allocation of 60 and unallocated credit of 40, then assert exact money, wallet, allocation and charge outcomes. Rejected operations are checked in the same transaction after an explicit flush, then again after rollback, against complete ledger/allocation/audit snapshots. Independent PostgreSQL sessions queue both void-first and refund-first contenders behind a controlled student lock. The tests require one committed winner, exact reversal amount, exact audit fields and cardinality, exact allocation reversal/survivor history and the expected remaining wallet credit.

The first FAIL audit found that rollback could mask writes made before rejection and concurrent assertions were too broad. The executor added in-transaction snapshots and exact history checks. The second FAIL audit demonstrated pending ORM writes still escaped because autoflush is disabled, and audit set equality could hide duplicate rows. Root added explicit snapshot flushing and audit cardinality. Both previously unobserved behaviors now have detected mutations. Independent read-only review approved the corrected invariants and transaction boundaries.
