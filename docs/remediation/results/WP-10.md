## Behavior and review

Both reset CLIs require `--reset`, an exact expected database identity and absolute storage identity. Production is refused. Database URLs must be PostgreSQL loopback targets with explicitly recognized disposable database names and no query/fragment overrides. Storage must be the backend's existing nonsymlink storage directory with a matching disposable-ownership marker. Business entrypoints revalidate authorized targets against current settings. Dry-run performs no provisioning, database or download work and prints only safe target metadata.

Fixed credentials and credential output are removed. Secure terminal provisioning requires matching passwords of at least 16 characters and forces password change for seeded users. `GetPassWarning` is treated as an error before getpass's echoed-input fallback reads a password. Downloaded assets are staged before reset. Database reset/seeding uses an encompassing transaction; filesystem replacement stages beside the owned storage root, retains an owned backup until commit and restores it on normal failure. This is bounded failure recovery, not a distributed transaction or crash-recovery guarantee. Failed backup cleanup is reported without credential contents; interruption during filesystem replacement may require operator recovery of the retained backup.

Review covered correctness, readability, architecture, security and performance. New guard, provisioning and storage-replacement responsibilities are encapsulated in separate classes; existing script entrypoints remain. No unrelated business behavior, schema, data retention policy or frontend source changed.
