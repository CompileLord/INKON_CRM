## Resulting behavior

Financial writers acquire a transaction-scoped PostgreSQL row lock on the existing student account before reading availability or making changes. Payment, discount, adjustment, manual and automatic allocation, refund, void, schedule generation, enrollment and withdrawal share this protocol. Multiple accounts use distinct IDs and SQL ordering by ID. Nested enrollment/schedule/allocation calls retain the lock in the caller's transaction; the service does not commit early. Aggregates are read after acquiring the account lock. Accounting-period closure remains the separate WP-36 protocol.

The ledger has a partial unique index on the reversed payment for void entries. Migration `e1f7a8c9d0b2`, parent `c9e3f0a1b2c4`, refuses duplicate existing void history before creating the index. It neither repairs nor deletes history. Downgrade drops only this index. Money remains Decimal, reversals remain append-only and authorization boundaries are preserved.

The sample sizes are small; results are local contention evidence, not production capacity estimates.

SQL cursor timings include query overhead and are not pure lock waits. Root therefore ran a second matched committed-transaction driver with a separate observer connection sampling PostgreSQL `pg_locks.waitstart`. It recorded the maximum observed wait age for each transaction. These are measured lower bounds: the observer sleeps 5ms between queries, query time adds to that interval, short waits can be missed, and zero means no observed wait. The observer was present in both before/after runs, which again ran sequentially in a confirmed idle window.
