## Data meaning and authorization

| Display concept | Existing source and exact meaning | Implementation rule |
| --- | --- | --- |
| Course balance | Debts endpoint: one student/course enrollment balance; default ordering is descending debt then stable enrollment ID | Keep student and course visible together. Do not call five rows five unique students or aggregate a fetched page into a student total. |
| Due unpaid | DebtItem.debt: due charges less active settlement allocations | Decimal string, prominent; distinct from contracted price and future installments. |
| Settled against due charges | DebtItem.total_paid is an allocation aggregate, including sources other than cash such as discounts | Never label this Amount paid or Cash paid. Explain its scope in Details. |
| Current receivable and unpaid students | Analytics computes current balances and distinct unpaid-student count | Label as current; do not imply that changing the collection range creates a historical snapshot. |
| Net cash collected | Analytics collected_in_period: period cash payments excluding voided payments, less period cash-out refunds | Show the explicit Dushanbe date range and refund explanation. A negative value or zero can be valid. Do not reconstruct it by summing a payments page. |
| Payment | PaymentItem.amount is original cash received; allocations may span courses | Keep original amount, allocation context and void/refund status distinct. Never quietly net a discount into cash. |
| Receipt/payment detail | Receipt supplies reference, identity, accepted-by and current active allocations; PaymentItem supplies void/refund fields | Combine the available records without claiming an immutable issued snapshot. No status inference from the receipt alone. |
| Audit record | One changed field, with actor/action/entity/reference/time and old/new string or null values | Count changes/records, not business operations; several create records can describe one payment. |

Finance reads, payment creation and receipt access use require_accountant, which permits superadmin/accountant. Student search/profile endpoints support accountant for the payment picker; this does not authorize navigation to staff student/course pages. Accountants remain inside Finance. Superadmin can use authorized student profile links. Audit remains superadmin-only. Existing void/discount/allocation hooks do not expand this UI's mutation scope; refund/adjustment/period management also require their own workflows and permissions. No new refund, discount, void, allocation or period-close controls ship in this redesign.

Read endpoint guards again at implementation time, including endpoints proposed for filter-option lists. Do not fetch staff-only courses or one profile/photo per row to beautify Finance. Debtor rows and picker results use text identity; no finance avatars or photo requests.

## Finance navigation and state ownership

Route /finance exposes Overview, Debtors and Payments as accessible tabs under one H1 and one global Accept payment action. Header is title/action side by side when labels fit; on narrow phones the action wraps to its own 44px row. Tabs are a full-width three-column strip on phone, each with a minimum 44px target and wrapping labels. Use selected semantics and keyboard navigation; selection and panel changes are immediate, without sliding underlines or page fades.

Define a typed frontend URL schema for selected tab, each registry's page and supported applied filters, and the overview collection range. These are new frontend route state, not claims of new API support. Validate enums/positive IDs/pages/date bounds, ignore unknown state safely and serialize only the owning endpoint's supported parameters. Switching tabs restores the previous tab's query/page instead of resetting it. Changing a server filter resets only that registry's page to one; Browser Back/refresh restores applied state. Preserve scroll and focused row when returning from Details/payment. If refreshed totals remove the current page, move to the last valid page and announce it without losing the successful payment reference.

Debts currently supports course_id, min_debt, overdue_days, enrollment_status, page and page_size. It does not support student_id, enrollment_id, text search or arbitrary sort. Payments supports student_id, course_id, method, recorded_by, date_from/date_to and pagination; its course filter means payments with allocations on that course. Audit currently supports pagination only. Expose only actual capabilities and accurate scope labels.

Use a clearable course context only when its identity comes from authorized data; do not fabricate a complete course selector from one fetched page.

The Filters surface uses the shared dialog: about 480px desktop; safe-area bounded phone surface with one scroll body and footer Apply/Clear. Offer overdue-days threshold, enrollment-status selection and minimum due amount with precise labels. Show supported course context and Clear when supplied by navigation; a global course picker requires a separately verified authorized option source. Filter edits remain draft until Apply; Cancel/Escape discards filter draft. Money threshold stays a decimal string; the existing float min_debt backend parameter must be corrected by the precision task before enabling a money-threshold control that claims exactness. Until then omit that control, preserving other supported filters. Applied chips wrap, remain visible on empty/error results and expose 44px removal targets.

Desktop table default columns: Student/course, Due unpaid, Days overdue, Actions. Identity uses name then wrapping course and optional small student reference; due amount is right-aligned/tabular. Days overdue zero has neutral text, never a red zero-days pill; unknown/invalid values use an unavailable label, not zero. Actions are Accept payment and Details, accessible independently. A superadmin name link can open the authorized profile; accountant identity remains text. Row hover is quiet and capability-gated, without lifting/scaling the whole row.

Phone: one divided bg-card list, not separately elevated row cards. First line name and amount if room; next line wrapping course. Then labeled overdue duration and an action row with Accept payment plus quieter Details. Allow natural row height with 12–16px vertical spacing; at 320px or large amounts place amount on a labeled line. No avatar, hidden horizontal action, swipe action or hover-only affordance.

Do not collapse a focused child or animate height. Keep one row's expansion state while opening/closing payment; identity and primary action stay visible. If a detail depends only on the loaded row, it needs no separate request or spinner.

Pagination appears below the list with localized record range, server total labeled course balances and 44px previous/next controls; no claim that row total equals unpaid students. A failed refetch retains previous data with a stale/error indication. Opening a debtor payment passes exact student/course IDs and displayed names; Cancel makes no write. A successful refresh may settle/remove the originating row; restore focus to the next row or registry heading if the original action disappeared.

## Payments registry and payment detail

Course/recorded-by filters may be represented only from verified authorized context; do not add unsupported free-text/global-payment search. Date filter bounds represent inclusive Dushanbe calendar days converted deliberately to the datetime endpoint bounds. They are separate from the Overview collection range. Show all active context and Clear; filtering resets this page only.

Desktop table: Payment reference, Student identity/reference, Allocation summary, Cash received, Method/date, Status, Details. Use Payment #ID until the receipt supplies its actual receipt number; do not synthesize a receipt number in the frontend. Before joined name enrichment, display localized Student #ID explicitly. Do not query profiles per row. For one allocated course show its title; for multiple courses show the translated count of distinct allocated courses and expose full allocations in Details. No allocation is a truthful separate state, not an assumed course. Keep void/refund labels visible beside the original cash amount; ordinary recorded payments need no loud green badge.

Phone: divided rows with payment reference and date, student identity/reference, amount/method and a status line where meaningful; optional two-line allocation summary and 44px Details action. Values remain selectable; no tiny desktop columns. Long names and references wrap. Unallocated/partly allocated must not be mislabeled as the student's spendable wallet, especially after refunds. Use exact response meanings rather than inventing net-cash or available-credit calculations.

Details opens the shared read-only 560px desktop dialog, full-height safe-area surface below 640px. Header includes Payment #ID and Close. Body order: actual receipt reference when available; student identity; original cash received; method/date and accepted-by; known void/refund state from the payment record; current active allocations as divided rows with course, due date and decimal amount; optional comment. Label allocation section Current allocations. A voided or refunded payment must not look newly valid simply because its receipt endpoint returns the original amount. Neither receipt nor detail promises an immutable issued document; no download/export/share control is added.

The opener supplies the latest PaymentItem or successful create result, while the receipt query supplies identity and receipt fields. Keep their provenance explicit internally: do not overwrite void/refund metadata with absent receipt fields. Revalidate the originating payments query where possible. If the item can no longer be found or status refresh fails, preserve the last-known labeled state and show status unavailable/stale with Retry; never default to not voided or claim freshness from receipt data alone. An arbitrary deep link to payment detail without usable PaymentItem status is outside this first frontend workflow and would require a suitable detail contract.

Receipt initial loading reserves header/metadata/allocation geometry; failure offers receipt-only Retry and keeps known payment reference/status. No allocations explains that none are currently assigned; this is distinct from failed loading. Whole payment list empty explains whether no payments exist or no matches fall in filters, with Clear/Accept payment as appropriate. All mutations remain outside this read-only surface.

## Payment entry and completion

Use one payment form owner shared by Finance and the Group 01 dashboard; do not build separate simplified variants. Opening it closes shell previews through the shared overlay owner. Form dimensions: desktop width up to 520px, 24px padding, 16px radius, maximum height calc(100dvh - 48px); below 640px use full viewport width/height bounded by dynamic viewport and safe-area padding. Structure is header / minmax(0, 1fr) scroll body / footer. Header/footer are layout rows, never input-covering fixed overlays. Only body scrolls; contain overscroll and lock the background with cleanup on close. Footer may grow for wrapping labels and stays above the visible keyboard through shared viewport handling, verified on hardware.

Header: translated Accept payment and 44px Close. Body order: student identity, priority course, allocation explanation, Amount (TJS), Date, Method, optional Comment. Gaps 16px. Desktop amount/date can share two columns; phone uses full-width amount then full-width date. Cash/transfer is an accessible two-option radio group, each target at least 44px, wrapping rather than clipping. Do not use a dollar icon as the currency label. No repeated green Total to credit box, always-visible discount advice or additional confirmation modal. Footer contains one compact decimal amount/method summary, Cancel and Accept payment; primary action is full-width on narrow phones with a separate secondary row if needed.

General entry starts with an empty student picker. Search uses the existing authorized students endpoint; each result shows full name plus localized student reference and email as secondary disambiguation, never photo-dependent identity. Search is keyboard navigable with announced result state, visible focus, Escape returning to input and bounded result scrolling. Use its actual pagination/total and a reachable More results control when truncated; do not silently restrict selection to the first eight matching names. States cover searching, request error/Retry, no match with query guidance and results. Selecting a student is read-only and keeps the stable reference visible. Change student clears the course and stale course data before a new selection is possible.

Load eligible course context from the permitted selected-student profile, not a forbidden course-detail route. Course loading, error/Retry, no available enrollment and loaded options are distinct. Use the existing server enrollment eligibility; do not invent an active-only policy or infer eligibility from a course title. Server rejection of an unavailable enrollment retains entered money/date/method/comment and shows a recoverable field error. Disable submit until the current student/course context is valid.

Debtor entry displays its actual student/reference and course as a quiet labeled context block, locked for that flow. It does not render disabled-looking editable fields. Amount starts empty, ready for explicit cash entry; do not auto-submit or silently assume full debt. The amount received may differ from due unpaid. Beside priority course, translated help explains that this course's charges are settled first and remaining credit may settle other open charges, with any remaining unapplied value retained according to the ledger. Do not predict an exact course reduction or invent a pre-submit allocation preview. Existing credit may also participate in the server's allocation workflow.

Use string input state and inputmode decimal, with explicit decimal parsing/validation via existing helpers. Handle the supported locale decimal separator deliberately and serialize the canonical decimal string without parseFloat/Number. Reject empty, invalid and nonpositive amounts with a visible field error; do not silently return on missing IDs. Do not add a rounding/precision business rule beyond the synchronized backend contract. Amount must retain exact value through retry and submission.

Date defaults at each new form opening to the Dushanbe calendar date, using a shared date helper rather than UTC toISOString slicing. A date-only selection is interpreted deliberately as the chosen Dushanbe day when converted to the payment datetime; do not let the device timezone shift it. Shared formatters must support the needed explicit timezone/date-only semantics rather than page-local formatters. Keep the chosen day during responsive/theme/locale changes and failures. Closed-period or other business rejection produces translated actionable feedback; do not add period-reopen actions here.

Initial focus is student search for general entry, Amount for a valid prefilled entry, or the first unresolved context field. Form errors focus the first invalid field and announce the error summary. Pristine Cancel/Close/Escape dismiss immediately without writes. When user-entered values differ from the initial form, dismissal/navigation requests use the shared Keep editing / Discard changes decision in the same modal ownership flow, focusing Keep editing by default; discarding only clears this unsaved form. Do not stack competing modal focus traps. Breakpoint/theme/locale changes preserve the live form and values.

The mutation owner drives pending. Pending disables repeat submit and form edits and prevents modal dismissal/navigation that would lose the in-flight result; expose an announced Recording payment status without animation delaying the request. Release those restrictions on settlement. A confirmed rejection keeps all values and permits correction/retry. An ambiguous transport result must not be presented as proof that no payment exists; preserve values and explain verification is needed before resubmission. No automatic mutation retry or claim of server idempotency is added by a disabled button.

On confirmed success, retain the returned payment ID/record, close the form and show a durable translated success region in the originating Finance/dashboard pane containing Payment #ID and View payment. An optional toast is supplementary; disappearance of a toast must not remove the only result link. Reset the form only after success is retained. View payment opens the read-only detail using that returned record, even if the list's active filters exclude it. Receipt loading/failure is independent and must never offer Submit payment again.

Invalidate relevant finance-root queries, affected dashboard finance data and any separately keyed cached balance/payment context. Keep filters, tab, page, originating scroll and result message during refresh. Do not optimistically remove balances or claim the full debt is settled before refreshed server state. A balance/receipt refresh failure preserves the successful payment reference and local Retry. Focus returns to the initiating control or a logical heading/adjacent row if it disappeared; when the user opens View payment, focus goes directly to that detail.

## UX overrides from the screenshot review (2026-10-16)

- **Rows read as sentences, not database dumps.** Each row reads "<Actor name> <verb> <entity label> · <relative time>".
