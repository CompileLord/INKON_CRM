# Independent review — Group 02 staff courses

Status: recommendations for approval; baseline plans and application unchanged. Scope is superadmin and mentor `/courses`, `/courses/:id`, and their course/enrollment surfaces.

The baseline makes the right structural decision: a compact course identity followed by Overview, Students and Progress. Its remaining weakness is implementation ambiguity. A developer could follow it literally yet produce an overcrowded header, a misleading grade summary, an unusable mobile comparison table, or editable-looking fields that the API rejects. The additions below resolve those gaps rather than repeat the existing redesign checklist.

## Motion and library decision

No additional page-specific motion pattern passes the gate beyond the already approved surface and press recipes. These are applications of `MOTION.md`, not an expansion of its five-pattern budget.

| Location | Today / evidence | Purpose | Frequency | Exact accepted recipe and gate |
| --- | --- | --- | --- | --- |
| Course action menu, enrollment and course form | Open surfaces captured; their actual timing was not captured | Spatial consistency / preventing a jarring change | Occasional | Existing bounded-surface recipe: opacity 0→1 and scale .96→1, 200ms ease-out, menu origin at trigger, dialog centered. CSS and `motion-safe:` only; do not scale the background page. Gate passes because readable underlying data stays still. |
| Enroll, Save, Retry and overflow controls | Small controls observed; timing unverified | Feedback | Tens/day | Existing press recipe: 1→.96, 150ms ease-out transform transition under `motion-safe:`. Immediate disabled/pending state with stable button width. Gate passes only for control feedback; submission never waits for animation. |

Reject tab-panel fades and sliding page content: frequent reading/navigation fails the function gate. Reject chart drawing, animated score ramps and rolling averages: users compare exact values. Reject roster insertion/removal animations and card staggers: they move the next target during operational work. Reject swipe-to-withdraw, draggable forms and hold-to-delete: these introduce gesture complexity or timings outside the project's contract without a demonstrated need.

`frontend/package.json` was inspected. Keep its installed router, query, form and state tools. Reuse the shared accessible surface primitive selected in Group 01; this group does not justify an independent Base UI installation, toast replacement, table library or virtualization package. No live animation feel, keyboard focus trap or device touch behavior is claimed verified.

## Baseline recommendations to remove or narrow

These are proposed cuts to the **planned** design, not additional descriptions of defects already visible in the old application. They reduce scope while preserving the underlying information.

| Exact baseline recommendation | Decision and reason | Replacement / evidence / risk |
| --- | --- | --- |
| `/courses`: “three compact counts in one strip” and desktop “a shallow summary strip” | **Remove the mandatory three-metric strip.** Total courses duplicates the title count; active courses duplicates a status filter; system enrollment count does not help choose a course. For mentors, the third number is unavailable in the captured view. Compressing these into smaller cards preserves an unnecessary reading step. | One course count beside the title; status choices directly above results. If reliable global status counts already exist, append them to the corresponding filter labels without a separate metric region. Keep organization-wide enrollment totals on the dashboard. Evidence: both list contact sheets and `screenshots/superadmin-courses-desktop-light.png`. Do not derive global counts from one result page. |
| Progress: “a muted heatmap is optional” | **Remove heatmap from the first implementation scope.** It duplicates the numeric comparison table, introduces a second control/state/color system and makes grade magnitude look like semantic status. The captured dense color block is exactly the visual dominance the user wants reduced. | One neutral desktop comparison table and the phone period view specified above. Retain risk indicators only when supported by the domain. Evidence: both detail contact sheets; full-size desktop light/dark originals. Reconsider a heatmap only if a concrete staff comparison task proves difficult with the table. |
| Progress: phone “an explicit Compare periods mode can scroll horizontally” | **Defer the additional phone mode.** A horizontal table is a valid escape hatch, but there is no captured use case showing a second phone presentation mode is necessary. Building it now adds controls, persistence and accessibility work before the primary phone task is usable. | Initially ship the period selector and student scores on phones, with desktop comparison available. Keep the geometry proposal in must-fix item 3 as the specification if comparison is later approved. Evidence establishes current clipped comparison, not demand for a second mode. Risk: users who genuinely need simultaneous periods on phones would need that follow-up; do not claim their need has been researched away. |
| `/courses` phone: “Grid preference remains available where it fits” and separate desktop preference persistence | **Narrow to a responsive default first.** A phone row/grid chooser changes density without adding course information, and creates extra toolbar state at the narrowest width. | Phone uses compact rows; desktop may retain its existing row/grid choice. Switching breakpoints changes presentation automatically while preserving query/filter state. No phone view toggle or independent phone view-preference store. Evidence: both list contact sheets show controls competing with results. This is a simplification proposal, not evidence that users never prefer cards. |
| Overview: “Show the next scheduled lesson only if the existing schedule/date model can calculate it correctly” | **Defer the next-lesson feature unless an authoritative dated occurrence already exists.** A weekly pattern plus course dates can miss cancellations, timezone rules and exceptions; a speculative “next” promise is worse than an accurate schedule. | First release displays the weekly schedule already supported. A dated next lesson is a separate product/contract decision if the existing model cannot establish it. The full-size detail captures show a weekly schedule only; no next-occurrence behavior was captured. |

## Worthwhile additions and interface changes

Prefer the following small workflow gains over adding more charts, metrics or presentation switches. The first group uses existing capabilities; the second identifies genuine product/backend work that must not be hidden in a visual implementation.

| Scope | Feature or interface update | Concrete behavior and value | Dependency / acceptance |
| --- | --- | --- | --- |
| **Existing capability: mentor course list** | Add a direct Open journal action to each assigned course row. | Course title still opens Overview. A sibling labeled journal action opens the existing course journal route, saving a detail-page visit for the recurring teaching task. On phones put the action beneath metadata in the row, rather than stealing title width. Keep it visually secondary to course identity. | Existing detail already exposes this authorized route. Verify the exact journal guard for mentors and keyboard link order; never nest links. No new recent-course ranking, activity tracking or endpoint is required. Value is inferred from the existing journal action, not measured user research. |
| **Existing capability: detail return paths** | Preserve the precise work context across student/journal navigation. | Returning from a student profile restores Students with its search and scroll position; returning from journal restores Progress with the selected period when that was the entry point. Explicit detail Back returns to the prior filtered course list, with a safe `/courses` fallback for direct entry. | Builds on the baseline tab query parameter, extending it to a complete return path. Router state/query values must be validated; a stale/deleted period falls back visibly to an available period. No browser-history dependency that can accidentally send a directly arriving user outside the app. |
| **Existing capability: enrollment result** | Make success observable in the roster, not only in a toast. | After successful enrollment, close the picker, stay on Students, refresh the count and show the new student's row. If the active roster search would hide that person, offer a translated View enrolled student action that clears the conflicting search. On failure retain selected identity and readable inline error. | Existing enrollment mutation and roster refresh suffice. Preserve scroll unless the user chooses to reveal the student; no unsolicited animated insertion or page jump. Test a successful enrollment while a conflicting search is active. |
| **Existing capability: content structure** | Keep actions and facts in one predictable location. | Identity header owns Open journal and the admin menu. Overview owns schedule, description and the small metric strip. Students owns enrollment/status/price. Progress owns grades. Course price remains in identity; per-student price remains in Students because it is an enrollment snapshot. Remove redundant grades and description snippets elsewhere. | This is the ownership rule behind the tab redesign, useful to a future implementer making component boundaries. Do not merge course price and enrollment price: source already distinguishes them. |
| **Backend/contract improvement, conditional** | Supply eligible-student pagination and a bounded course roster response. | A server-filtered picker prevents excluded students from consuming an entire search page. A course-scoped roster containing authorized identity, enrollment terms and supported course metrics avoids per-student profile fan-out. | Worthwhile at larger rosters; implement in service/repository layers with authorization, paging and query-count tests. Do not bulk-fetch unrelated student profiles or disguise incomplete results as complete. Requires explicit schema/type/contract work. Existing pagination remains a truthful interim option for the picker. |
| **Product/contract expansion, deferred** | Dated next lesson, cell-specific journal deep links, editable enrollment terms. | These may become useful, but each needs a clear domain and navigation contract first. A period cell should link only if the destination selects that exact period/student; next lesson needs actual occurrence rules; editable terms need authorized supported fields. | None is necessary to deliver the approved calmer course pages. No invented data, new route assumptions or extra form controls in the first visual release. |

Do not add a course activity feed, favorites system, bulk enrollment, new chart dashboard, swipe actions or another onboarding illustration merely to make the redesign feel more substantial. The evidence supports quicker access to existing work and clearer state, not a larger feature inventory.

## Approval and implementation boundary

Approve the first six clarifications before changing the baseline plan. Then incorporate useful additions where they fit shared components. This review does not authorize scoring changes, expanded enrollment terms, mutable course terms, new API permissions or invented next-lesson data. All implementation inherits the baseline token, locale, four-state, decimal-money and verification rules.

Only this review file was written. No app/source, baseline plan, token file, live application or Taskmaster task was changed; no commit was made. Application test suites were not run because this is a documentation-only review, not implementation verification.
