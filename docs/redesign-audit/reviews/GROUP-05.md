# Independent review — Group 05: finance and audit

Review only; proposed amendments for user approval. Baseline plans, tokens and application files remain unchanged. No new capture, endpoint probe, payment submission, installation or commit was performed.

## Assessment and evidence

The baseline correctly prioritizes readable phone rows, visible payment actions, decimal strings, honest filtering, independent states and a human-readable inspector. Keep those decisions. Its main remaining weakness is the meaning of the information: an enrollment balance can look like a student's total, settled charges can look like cash paid, and a course preference can look like an exclusive payment destination. Correcting these is more valuable than adding another finance visualization.

## Worthwhile features to ADD or IMPROVE

### Design and frontend behavior using existing endpoints

1. **Close the payment task with a durable, identifiable result.** Show a translated success message containing the returned payment reference and a View payment action; preserve the originating debt list and its filters. The receipt detail should show original cash amount, method/date, student identity, allocation lines and current void/refund status from `PaymentItem`. The receipt response alone has no void/refund fields; do not drop the list item's status when opening it. Its allocations are current active allocations, not an immutable historical receipt snapshot. Evidence: the captured form is the entire visible handoff; baseline only specifies query invalidation. Dependency: existing creation result, receipt endpoint and permission-checked finance APIs. Risk: receipt loading failure must offer retry without repeating payment submission. No download/export promise.

2. **Disambiguate people in the student picker.** Each result uses full name on the first line and a supplied stable reference or email on the second. Keep the same identity after selection; use a 44px minimum result target and 16px input. Evidence: `PaymentModal.tsx` currently displays name only; the debtor list demonstrates repeated names and multiple-course context. This improves the already-planned picker without profile-fetching each result. Verify what the existing students response provides before choosing its secondary text.

3. **Make audit comparison understandable without color.** For update records, show a translated field label, then Before and After sections; on phone stack them vertically. For creates, use a value/added-field presentation instead of repeating “null →” for every row. Preserve actual null, empty and zero distinctions. Render known `PaymentMethod.CASH`/`TRANSFER` values as translated method names; preserve unknown raw strings in detail. Evidence: `superadmin-audit-desktop-light.png` and the inspector originals show serialized enum text and crossed-out nulls. This extends the baseline's action mapping to field/value presentation; it requires a small explicit display map, not heuristic parsing or a new API.

The redesign must not claim end-to-end exactness merely because frontend types are strings. Isolate any correction into a tested backend precision task; the integer-valued screenshots cannot verify precision.

## Motion and library verdict

No additional library is justified. `package.json` already supplies React Query, React Hook Form, Zod and big.js; finance should reuse them. Reuse the shared accessible dialog primitive if Group 01 adopts Base UI; this group should not introduce its own dependency migration. No chart, number animation, syntax-highlighting or gesture package.

| Location | Today | Purpose / frequency / function gates | Suggested motion |
| --- | --- | --- | --- |
| Payment and audit surfaces | Separate custom overlays | Occasional; spatial consistency; settles before reading | Reuse shared `card-scale-in`/surface opacity and scale .96→1, 200ms ease-out, `motion-safe:`; no extra effect. |
| Accept payment, retry and Details controls | Inconsistent press feedback | Tens/day; immediate feedback; does not move ledger data | `motion-safe:` transform transition 150ms ease-out with press .96; disabled controls stay still. |

Reject animated balance reductions/counting: function gate, financial values must be immediately readable. Reject staggered audit/debtor rows: frequency/function gates. Reject animated accordion height: shared token contract forbids layout-property animation. Reject celebratory payment effects: this repeated operational action benefits from a stable reference and result, not spectacle. These reuse two shared patterns and add no motion budget.

## Acceptance additions and limits

Add explicit regression cases for a student with two unpaid courses; discount settlement shown without being called cash; surplus allocating across courses; current balance staying current when the collection period changes; payment detail retaining void/refund status; and audit field rows remaining distinct across pagination. Verify picker ambiguity, 320px amount/date layout, three locales and both themes. Source-backed behavior proposals still need the full mandated implementation suites and contract regeneration where applicable.
