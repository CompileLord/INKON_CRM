Only superadmin has this directory route in the current frontend. The list API's additional permitted roles do not authorize new directory navigation. All account mutations remain admin-only. ## Create/edit forms and independent avatar persistence

Background content is inert while the dialog is active; preserve and restore its scroll position. Shared shell bottom navigation must not cover the footer.

Phone forms use one column for every field, including first and last names. Pair fields only in wider drawers when each remains readable at the 16px input minimum and errors wrap. Sections are Identity, Contacts and student Payment details, separated by space rather than extra cards. Identity includes names, email and optional birth date; Contacts includes ordinary phone first, then student parent phone and optional notification identifiers. Explain what an identifier is used for; entering a Telegram identifier is not proof of an active connection. Mentor forms omit student-only payment and parent-finance fields.

Use correct email/tel/input modes and autocomplete, E.164 telephone validation and translated placeholders/help. Student payment day follows the actual 1–28 contract. Mark required versus optional fields in translated copy. Every input has an associated label, help and error ID; invalid fields use `aria-invalid`/`aria-describedby`. Duplicate email maps to the email field. Failed submit retains entries, reveals the first invalid field and focuses it without smooth scrolling. General server failures remain visible inside the form until corrected/retried, not only in a toast. PATCH contains dirty fields only; clearing an optional value follows the actual API semantics.

### Focus, pending and dismissal

On phone opening, focus the dialog heading so the keyboard does not immediately conceal context; keyboard users can then tab into fields. On wider layouts, focus the first appropriate field unless an error needs attention. Trap focus within the shared dialog and restore it to the actual invoking Add/Edit control after closure, or to the profile/directory heading if the trigger no longer exists.

The footer observes the real mutation state. On submit, prevent duplicate requests, reserve button width, show translated Saving, and expose `aria-busy`. Keep the surface open until the operation resolves; while an identity save is pending, close/X/Escape/backdrop/Cancel cannot imply cancellation. Disable dismissal with a visible Saving state, then permit it after success/error. Do not silently abort a server write or clear the form because the user clicked the backdrop.

When no mutation is pending, pristine forms close immediately. X, Escape, backdrop and footer Cancel all use the same dirty-state decision: unsaved identity fields open one shared Discard changes/Keep editing confirmation. Keep editing returns focus to the field; Discard closes and restores the original trigger. Browser/app navigation during a dirty form must honor the same leave decision where the router supports blocking; do not add unrelated durable drafts. An unchanged edit should not send an empty PATCH.

### Avatar is a separate saved operation

Avatar upload requires an existing account ID and is available in edit mode only. Keep the existing immediate upload semantics explicit beside the control: photo changes save immediately, separately from the form. Show independent Uploading, Saved or Error state; a failed upload does not dismiss the form or lose identity edits. Reserve the avatar geometry and retain the previous successful photo if replacement fails. Show real measured progress only when available; otherwise use an indeterminate operation label.

After a successful avatar upload, Cancel discards unsaved identity fields only and clearly states that the saved photo remains. The no-write cancellation test applies to identity submission, not to an already completed photo operation. While an avatar upload is pending, prevent form dismissal until it settles or its explicit Cancel upload action resolves; do not claim transport abort rolls back a completed server write. Reconcile the persisted photo after cancellation/race completion. Upload success refreshes avatar data without resetting dirty identity values.

A new staged-upload/all-or-nothing Save model is deferred as a changed workflow; do not accidentally imply it through the footer labels. After creation, the new profile's contextual Edit makes photo upload available without returning to the directory.

### Accepted files and upload feedback

Source inspection found a concrete mismatch: `DocumentsTab.tsx` caps selection at 20 MiB and advertises DOC/ZIP; `DocumentService` accepts audio/image MIME families, PDF, DOCX and plain text with a **50 × 1024 × 1024 byte (50 MiB)** maximum. Align the picker, client checks, translated help and boundary tests with the current backend ceiling and accepted MIME families. Do not advertise legacy DOC or ZIP. Supported image/audio subtypes still need actual contract tests, including the service's magic-byte checks; a broad picker filter is not a guarantee that every file extension will pass validation. Unsupported-type and invalid-content server responses must remain distinct actionable errors. Do not retain an unexplained stricter 20 MiB frontend limit.

After selection, show owner name, filename and operation state inline. Disable duplicate upload submission. Keep a persistent inline error with retry/reselect and retained filename context; success/error toasts are supplementary. Clear the native file input after client-side rejection as well as after requests so the same file can be chosen again. If the selected file remains in memory, Retry may reuse it; after navigation or lost selection, ask the user to reselect rather than pretending a file is still available. Measured progress is shown only from real transport information; otherwise show Uploading with no invented percentage. Changing profile or leaving an in-flight upload must not report cancellation of a server operation that may already have persisted; reconcile the destination list on return.

### Authorization and separate file-delivery dependency

Upload/delete endpoints require superadmin. The listing service restricts students to their own documents, permits mentors to list student documents plus their own mentor documents, and denies accountant access. The profile UI remains bound to the current authorized person and does not broaden navigation or file discovery. Changing the mentor-wide document policy is a distinct backend/privacy task, not a frontend filter tweak.

**File-byte privacy is a separate contract/security dependency.** Source shows `DocumentsTab` opening direct `file_path` URLs, local storage returning `/storage/...` paths and `backend/app/main.py` mounting that directory using `StaticFiles`. Guarded listing alone therefore does not establish authorization for downloading file bytes. This is a source-observed architecture risk, not a proven deployed exploit: no unauthenticated probing or private download was performed during the audit.

Define and test authorized document delivery in a separate backend/storage work package, including anonymous, cross-user and permitted-role behavior. The redesigned Download action must use the resulting authorized contract; do not claim files are private merely because mutation controls are hidden. Storage migration, any API schema changes and synchronization belong to that task.
